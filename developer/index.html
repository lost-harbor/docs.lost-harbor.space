Developer guide

Lost Harbor is Rust from end to end. One synchronous engine runs under two hosts. The native host uses WebSockets and SQLite. The browser host uses a Web Worker and IndexedDB. The Leptos client sends commands and renders engine messages.

On this page: setup, crates, plugins, content, playtesting, checks, API writing, site builds, deployment.

§Local setup

Clone the source repository with an account that has access. The source repository is private. This public documentation site does not grant source access.

Install rustup, then let the root rust-toolchain.toml select the pinned toolchain. Install the matching browser build tool:

cargo install wasm-pack --version 0.15.1 --locked
cd game
. "$HOME/.cargo/env"
./build-web.sh
./build-lab.sh --release
cargo run -p lh_server -- --port 8090 --bind 127.0.0.1

Open http://127.0.0.1:8090/. Add ?local=1 to run the browser engine. The native server saves to game/data/dev.sqlite by default. Browser mode uses IndexedDB on that origin.

Use port 8090 or higher. The server accepts --port, --bind, --web, --content, --db, --memory and --no-watch. Content reloads from disk during native development.

§Add a feature

Engine features are plugins. A plugin registers its commands, components, systems, content kinds and views through AppBuilder. Use Engine::builder().plugin(...) for a custom engine. Register standard game features in plugins::add_standard. Do not make a new plugin depend on editing another plugin’s internals.

The engine remains authoritative. Both hosts run the same rules. The client sends ClientMsg values and renders ServerMsg values. Messages use a JSON t tag.

Every window action needs a typed command. Route window and typed builder operations through the same content API and validation. The source file design/specs/COMMAND_PARITY.md records those pairs.

§Content and builder tools

World records live under game/content/<kind>/<id path>.ron. An id such as spindle:bar maps to a nested path such as rooms/spindle/bar.ron. Content files are the source of truth.

§Physical controls and galaxy placement

Items independently define mountable, unlisted, and positive user_capacity (default 1). fixed prevents pickup. unlisted suppresses room listings and every pickup selector, but preserves named interactions and existing discovery rules. Mounts and control items cannot stack. Control items normally stay listed. Reserve unlisted for deliberate edge cases, such as alien ships. The Thren lifeboat helm stays listed.

Bare pilot chooses the first visible Pilot control with free capacity. With several controls, it marks its choice and lists exact named commands. Named commands remain strict. Item menus use physical references such as pilot 2.helm. Opening a saved room copy restores missing authored fixed controls, not depleted loose loot.

controls: (label: "Sensor Mode", groups: ["navigation", "sensors"]) enables the Control System feature. Feature plugins register group labels and shortcuts with AppBuilder::control_group. content_check adds registry-aware validation to the shared builder path without changing another feature’s code. control_verbs registers feature-owned permission rules for chart entity menus. The controls plugin validates group ids. Group checks authorize typed commands and chart verbs. Do not infer permissions from room names or client layout. Ships use the shared station items in items/general. Small craft carry one general:helm couch with every group except Fleet. Crewed ships put general:bridge-helm in the cockpit, with flight and charts only, and spread the other work across rooms: engineering-console (Refueling, Repairs), mining-console, survey-station, recovery-console (Fleet), turret-seat, copilot-seat, sensor-panel and chart-table. The controls tests exercise representative consoles and independent groups in the holodeck. They do not check the equipment on authored ships. The engine never guesses between identical copies in one room. The failure lists their ordinals, such as 1.recovery. UsingItem addresses a runtime entity. Persistence restores its room copy and checks placement, features and capacity again.

System records define galaxy_position: (x, y) in static galactic units and representatives: ["star-id"] using their own place ids. The System editor provides coordinates, representative selection and a shared SVG placement preview. sysedit <system> galaxy <x> <y> uses the same save path. The first added place starts as the representative and remains editable. Removing the last representative requires selecting another before saving. The core stays at (0, 0). Gate content supplies links and direction. The projection boundary currently includes every system. Future discovery filtering belongs there. Galaxy distances are distinct from orbital units. The client renders the full galaxy as deterministic inline SVG: a painted, face-on barred spiral without SVG filters, and an animated black-hole core drawn in screen space. The galaxy radius is 9000 units. The authored sector spans about one fifth of the diameter. The Verge sits at (3300, -3300), about half way out, where Sol sits in the Milky Way.

Remote charts use separate client system and clock signals. They contain no contacts, local ship state or actionable verbs.

In the game, build opens builder mode. clist, cshow, cset, cadd, cdel, cnew and cdelete operate on registered content kinds. Use help building and command-specific help for exact syntax. Native builder edits write to the selected content folder. Browser edits stay as IndexedDB overlays on embedded content.

The labs are at /lab/, with /lab/ships/, /lab/portraits/ and /lab/names/. Rebuild with ./build-lab.sh --release. The labs share the game’s generator code. The name lab saves phrases only through an eligible loopback native server. Public static labs do not write source files.

Name lists live under game/data/names/. From game/, cargo run --release -p lh_content --bin import-names builds the lab corpus pack. Read game/data/names/README.md and SOURCES.md before importing or distributing that data.

§Isolated playtesting

Never let test builder edits write to checked-in content. Use a unique temporary folder and an in-memory database:

test_root=$(mktemp -d /tmp/lost-harbor-test.XXXXXX)
cp -R content "$test_root/content"
cargo run -p lh_server -- --port 8091 --bind 127.0.0.1 \
  --content "$test_root/content" --memory

The copied content isolates native builder changes. The labs and browser engine use embedded content, so they require a rebuild after source-content edits. Stop the test server when finished. Remove only the specific temporary folder you created.

The disconnected holodeck is included in every build. Development builds offer prepared operator, pilot, combatant and builder personas on the character screen. The pilot starts at a practice helm with money and crew. The combatant has a blade, a suit and a practice target. The operator and builder start at staging. Each account can take each profile once. Use separate accounts for independent users. The extra experienced-pilot profile exercises owned-ship setup.

The engine gates both profile listing and direct selection with debug_assertions. Use ./build-web.sh --dev for a development browser worker. The default release worker does not offer these profiles, even when a debug native server serves it. No exits or gates connect the holodeck to the normal world. Use the normal showcase pilot and a fresh newcomer for manual checks of the authored world. Browser saves and the native server database are separate.

§System test fixtures

Automated tests verify systems, modules and plugins, not authored content. They do not promise story completion, encounter win rates or fleet equipment. There is no separate authored-content suite. RON stays the source of truth. IndexedDB keeps browser state and builder overlays. A database migration is not needed for test isolation.

World-backed tests enable the lh_content test-support feature and call lh_content::holodeck::content(). The loader parses only the combined holodeck records, caches the immutable content once per process and returns a fresh clone. Each harness owns its engine, clock, random seed and store. Tests can alter that clone for a specific case. Independent start and timing rules live in lh_content/src/holodeck_rules.ron. Add only compact exercise props, not copies of authored adventures. Geometry tests build synthetic layouts. Name tests use tiny synthetic sample lists.

The production loader and builder still validate content. Tests of validation supply deliberate valid and invalid records. They never load the normal world to check it, and never read the real name corpus.

§Checks

Run from game/:

cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo clippy -p lh_client --target wasm32-unknown-unknown --locked -- -D warnings
cargo build -p lh_engine -p lh_worker --target wasm32-unknown-unknown --locked
cargo clippy -p lh_lab --target wasm32-unknown-unknown --locked -- -D warnings
python3 -m unittest discover -s tools -p 'test_*.py' -v
./build-docs.sh

The typed system exercises and template-policy check are:

cargo test -p lh_engine --test walkthrough --locked
cargo test -p lh_engine --release --test walkthrough template_availability_is_enforced_for_direct_requests --locked

Check interface changes in a browser at 1920x960 and 1600x860. Hard-reload after rebuilding browser assets. There is no service worker.

§Write API documentation

Use //! to explain a module and /// to document an item. Describe behavior, inputs and results. Add error and panic sections when those outcomes apply. Use intra-doc links for related types and methods. Rustdoc verifies those links. For a type in another crate, include its kind and absolute path, as in [`ShipView`](struct@::lh_protocol::ShipView).

Every public library API needs documentation, including fields, variants and associated items. The docs build fails on missing documentation or rustdoc warnings. Keep examples accurate and run workspace doctests. Use short sentences and the repository’s plain-English writing rules.

Library roots use #![doc(html_no_source)]. This stable attribute prevents source-code pages in the public API output. Do not enable private-item documentation for the published site.

§Build and preview this site

From game/:

./build-docs.sh
python3 -m http.server 8092 --directory pages/docs --bind 127.0.0.1

Open http://127.0.0.1:8092/. The build renders Markdown guides through rustdoc and generates all public library APIs. It documents workspace dependencies first so cross-crate links resolve reliably. It then builds the whole workspace to keep its shared feature selection. It checks page links and required crate pages, then packages game/pages/docs/. It also checks browser APIs on the wasm target. Generated output stays out of git.

The packager normalizes known upstream links from rustdoc, Leptos prop docs and tracing’s inherited trait docs. Its tests cover those repairs. Unknown broken links still fail the build. Rustdoc redirects retain method anchors during link validation.

Guide sources are in game/docs/. The guides and API use the lab’s dark surfaces, the wordmark’s orange accent and shared navigation. The API starts dark but keeps rustdoc’s theme settings. Edit style.css for guides, api-theme.css for the API, and header.css for their shared header. The build and package tools are game/build-docs.sh and game/tools/package_docs.py. Update guides when commands, content or development steps change. Do not publish future design plans as current behavior.

§Deployment

Source eventDestination
Validated push to mainDevelopment game and this documentation site.
Published stable releaseProduction game.
Pull request to mainChecks and downloadable artifacts only.

The documentation destination is lost-harbor/docs.lost-harbor.space. Pages serves its main branch root at https://docs.lost-harbor.space/. The source workflow uses DOCS_PAGES_DEPLOY_KEY, scoped to that hosting repository. Pull-request builds receive no deployment key.

Deployment preserves the destination’s CNAME and LICENSE.md. It replaces obsolete generated files without rewriting git history. An outdated source revision does not replace newer main documentation. deployment.json identifies the deployed source commit.

Repository permissions, DNS and HTTPS configuration are separate from a successful local build. Read the source repository’s game/README.md for hosting setup and first-rollout steps.

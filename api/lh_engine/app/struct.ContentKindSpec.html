Expand description

One content kind that the builder can browse and edit, such as rooms.

The owning plugin registers it with AppBuilder::content_kind. The building plugin then serves BuildOp::Kinds, List, Get, Put, and Delete for it without knowing anything about the kind. This is the Strategy pattern: each kind supplies its own summary, check, and apply steps, and the generic code calls them through function pointers.

Storage stays in lh_content. The kind key must name an entry of lh_content::KINDS, which reads and writes the record as JSON and RON. So a new kind adds a map to Content, an entry to KINDS, and one content_kind call in its plugin. The building plugin does not change.

Fields§

§kind: String

The key used in BuildOp and in file paths, for example room.

§label: String

The label shown in the builder, for example Rooms.

§icon: String

A Tabler icon name, for example door.

§summary: Option<fn(&Content, &str) -> ContentSummary>

Describes one record for lists. The record exists when this is called. None means the default: the record’s name field (or title) and no group.

§validate: fn(&Content, &str) -> Vec<Problem>

Extra checks for one record, beyond the cross-reference checks that lh_content runs. The content passed in already holds the new record.

§apply: fn(&mut World, &str)

Runs after a change to one record went live. It brings live entities in line with the record, beyond what the ContentReloaded observers do.

A kind with the default steps. The summary shows the record’s name field, there are no extra checks, and apply does nothing.

Rust note: a closure that captures nothing converts to a plain fn pointer, so |_, _| Vec::new() fits the validate field.

Crate lh_engine 

Expand description

Lost Harbor game engine.

Synchronous and transport/storage agnostic: the same engine runs inside the native server (WebSocket + SQLite) and inside a browser Web Worker (wasm32 + IndexedDB). Hosts call Engine::connect, Engine::handle, Engine::tick, Engine::drain and Engine::take_dirty.

Internally it is an ECS world (bevy_ecs) assembled from Plugins. See app for the extension points.

§How the crate fits together

  • The engine module holds Engine, the host API. The host creates an engine, opens sessions, sends client messages and advances time.
  • app holds the plugin system. A Plugin registers commands, views, systems and event observers on an AppBuilder. The result is a set of Registries that the engine reads while it runs.
  • queue runs typed commands for every actor, one at a time, with timed actions that hold the queue.
  • parse splits a typed line into a verb and arguments.
  • world defines the shared components and resources that plugins query.
  • edits keeps builder edits as an overlay on the content files.
  • plugins contains the standard gameplay features. Each one is a plugin.

§Adding a feature

Write a type that implements Plugin. Its build method calls the AppBuilder methods for each contribution, then add the plugin with EngineBuilder::plugin. Existing plugins and the core do not change. The tests/plugins.rs file shows a complete example.

Modules§

app
Plugin architecture.
ctx
The command context handed to every handler.
edits
Builder edits to the content, kept as an overlay on the content files.
events
Typed events and the observers that react to them. A small typed event bus (Observer pattern). Systems emit events. The engine dispatches them to observers registered with AppBuilder::observe after each command and tick. Publishers never know their subscribers. New features can react to existing events without touching the code that raises them.
instance
The shared record of live instance copies, and the clock of each copy.
parse
Command-line parsing. Command-line parsing: ; chaining, verbs, directions and keyword targets such as 2.ore, all.ore and 5 ore.
plugins
The standard gameplay plugins. Standard gameplay plugins. Each one is self-contained: it registers its commands, views, observers and systems and depends mainly on the core (world, events, ctx, queue). A few import a sibling, such as shops using items, so the rule is core-first, not total isolation.
queue
The action queue and the timers that drive it. The action queue: every actor (player, simulated player, NPC) runs typed commands through the same pipeline. Commands run in order. A busy command (walking a long tube, searching, resting) holds the queue until it completes. stop clears it immediately.
records
Records that the host persists between runs. Persistence plumbing. Record kinds are registered by plugins. The engine diffs their current records against what the host last stored.
rng
The deterministic random number generator. Deterministic random numbers (SplitMix64). No OS entropy, so the engine behaves identically on native and wasm, and tests can pin a seed.
rules
Dice rolls and the rules of the game. Rules: a 5e-derived sci-fi system in our own wording. d20 + ability modifier + proficiency (if trained) against a DC.
session
Connected sessions and their outboxes. Connected sessions and their outboxes.
text
Text helpers for articles, counts and markup links. Text helpers: articles, counts and lh_markup semantic links.
views
Builds the views that the engine pushes to sessions. Pushes views (room, map, vitals, …) to sessions when they change.
world
Shared components and resources used across plugins. Shared components, resources and helper functions used across plugins.
